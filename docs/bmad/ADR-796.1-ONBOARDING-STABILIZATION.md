## 2. Sécurisation des fichiers

**Principe** : aucun fichier venant du portail public n'entre dans le DMS avant une analyse « saine ». Une extension ou un type MIME accepté n'est jamais une analyse.

- **Quarantaine** : disque dédié `quarantine` (`storage/app/quarantine`). Il n'est jamais servi (`serve: false`) et n'expose aucune route de téléchargement. Chaque fichier reçoit un nom aléatoire (`onboarding/{société}/{dossier}/{uuid}.bin`). Une ligne `onboarding_uploads` garde la trace : nom d'origine, taille, empreinte SHA-256, état, moteur, signature, tentatives, dernière erreur.
- **Analyse** : `App\Core\Documents\Scanning\FileScanner`, un contrat transversal réutilisable par tout le DMS. Pilotes disponibles :
  - `none` (défaut) : aucun moteur, verdict toujours « indéterminé » ; ce pilote est fail-closed.
  - `clamav` : démon `clamd`, protocole INSTREAM, socket unix ou TCP. Il est prêt mais n'est pas installé en DEV.
  - `simulated` : adaptateur de test. Il reconnaît la chaîne EICAR (→ infecté) et un marqueur d'échec (→ indéterminé). Ce n'est pas une analyse : le moteur est enregistré et affiché comme « simulé ». Il est refusé en production, où l'on retombe sur `none` avec un avertissement journalisé.
- **Traitement** : `OnboardingUploadScanService::process`, idempotent. Il verrouille la ligne et ne traite que l'état `quarantined` ; un rejeu ne change rien. Il travaille dans le contexte tenant du dépôt via `ScanOnboardingUploadJob` (`InteractsWithTenant`, 3 essais, attente progressive). Selon le verdict :
  - **sain** : le fichier passe par le chemin de dépôt unique `SubjectDocumentUploadService`, devient une demande DMS « soumise », jamais validée, et la copie en quarantaine est supprimée. Les analyseurs du pipeline (images, PDF, OCR) ne touchent qu'un fichier analysé sain.
  - **infecté** : refusé, fichiers supprimés immédiatement, métadonnées et signature conservées, audit `warning`.
  - **indéterminé** (moteur absent, injoignable, délai dépassé, réponse inattendue, échec d'ingestion) : reste en quarantaine et est réessayé. Au-delà de `documents.scanner.max_attempts` (5), il passe à `scan_failed` : inutilisable, mais les RH peuvent relancer l'analyse.
  - **dossier révoqué ou purgé entre-temps** : le dépôt est écarté et ses fichiers supprimés.
- **Reprise après panne** : la commande `onboarding:scan-uploads` est planifiée toutes les 10 minutes et retraite tout ce qui est resté en quarantaine. L'option `--simulate` est réservée au DEV et refusée en production.
- **Exploitation interdite** :
  - La recrue ne voit jamais « validé ». Elle voit « analyse en cours », « refusé » ou « analyse impossible ».
  - Côté RH, chaque pièce affiche son état d'analyse.
  - La validation du dossier est refusée tant qu'une pièce demandée est en quarantaine, refusée ou indéterminée (`documents_not_cleared`).
  - Aucun `MemberDocument` n'existe avant l'analyse, donc aucune route DMS ne peut servir le fichier.
- **Isolation** : chaque ligne porte `company_id`, et la relance RH est limitée au dossier et à la société. Une autre société ou un autre dossier reçoit une réponse 404.
- **Suppression** : un fichier infecté est supprimé tout de suite, un dépôt remplacé avant analyse aussi. Les dépôts jamais entrés au DMS sont supprimés par `onboarding:retention` à l'échéance du dossier. La trace (métadonnées, audit) est conservée.
- **Historique** : aucun document existant n'est modifié. Les dépôts faits par les RH depuis la fiche personne ne passent pas par la quarantaine ; l'étendre est une décision distincte (voir §11).

## 3. Vérification du candidat

| Cas | Comportement vérifié |
|---|---|
| Lien transféré / plusieurs sessions | Chaque ouverture crée sa propre session. La vérification ne vaut que pour la session qui a saisi le code ; une autre session reste non vérifiée et ne voit pas les valeurs sensibles. |
| Lien expiré / révoqué | Réponse uniforme (404/401). Sessions supprimées à la révocation, à l'expiration constatée et à chaque nouveau lien. |
| Renouvellement | Le nouveau lien invalide l'ancien et toutes les sessions, remet à zéro le verrou et le code. Un dossier expiré reprend (`in_progress` s'il avait été commencé). |
| Code expiré / incorrect / réutilisé | Refusé. Le code n'est utilisable qu'une fois (empreinte effacée au succès). |
| Tentatives excessives | 5 par code ; **10 échecs au total** → `verification_locked_at`, envoi de code refusé, audit `onboarding.verification_locked`. Seul un nouveau lien émis par les RH lève le verrou. |
| Envois répétés | 5 codes par 24 h et par dossier, en plus de la limite de débit par IP. |
| Changement d'adresse | Opération RH tracée sans l'adresse. Le code en cours, le lien, les sessions, le verrou et l'état de vérification sont effacés : l'invitation doit être renvoyée. |
| Champs sensibles avant vérification | Ni lisibles ni modifiables. Pièces hautement confidentielles refusées. |
| Finalisation | Un dossier qui contient au moins un élément sensible ne se soumet que depuis une session vérifiée. Un lien ne s'émet pas sans adresse de la recrue quand le dossier contient un élément sensible. |
| Canal | Le code part immédiatement (jamais mis en file : il n'est jamais stocké dans une file de tâches) par le système de notifications. Sans canal transactionnel réel, l'accès sensible reste bloqué. Un échec d'envoi annule le code. Le code n'est jamais affiché dans une interface ni écrit dans l'audit. |

## 4. E-mail transactionnel en DEV

- **Envoi** : `OnboardingInvitationNotification` passe par le système de notifications Leezr, qui applique la configuration SMTP de la plateforme via `EmailEventSubscriber`. L'envoi est **immédiat** : le lien est généré et envoyé dans la même requête, sans jamais passer par la table des tâches. Chaque envoi crée un **nouveau lien**, ce qui invalide le précédent et ses sessions.
- **Garde-fou** : `TransactionalMailChannel::available()` est fail-closed.
  - Les transports `log` et `array` sont refusés (seul `array` est admis par le lanceur de tests).
  - Hors production, seul un SMTP **local** est accepté (127.0.0.1, localhost, mailpit). Un DEV mal configuré ne peut donc pas atteindre un vrai candidat ; l'interface propose alors le lien à copier.
- **Contrôles** :
  - Délai minimal de 2 min entre deux envois et 5 envois par 24 h. Ces compteurs sont pris sous verrou, ce qui empêche les doubles clics et les envois concurrents.
  - Le statut d'envoi (`sent` ou `failed`) est enregistré, avec une erreur nettoyée de toute URL.
  - Les événements d'audit `onboarding.invitation_mailed` et `onboarding.invitation_delivery_failed` ne contiennent ni le jeton ni l'adresse.
  - La réponse HTTP ne contient jamais le lien.
- **DEV** : Mailpit local (`127.0.0.1:1025`) ; la plateforme n'a pas de SMTP configuré. La recette lit le lien dans Mailpit. Aucun envoi externe.
- **Lien à copier** : toujours disponible pour les tests (« Créer le lien », « Nouveau lien »), affiché une seule fois.

## 5. Cycle de vie et expiration

- **Lectures pures** : la liste et le détail RH n'écrivent plus rien. Un dossier dont le lien est échu s'affiche « expiré » (`effectiveStatus`) avant même le constat. Le test compare l'état complet des lignes avant et après les lectures.
- **`OnboardingLifecycleService`** est le seul endroit où une expiration est enregistrée.
  - Chaque dossier est relu sous verrou, ce qui le rend idempotent et sûr en concurrence.
  - Il efface le lien, le code et les sessions et pose `expired_at`.
  - Un audit `onboarding.expired` est créé par dossier.
  - **Aucune donnée n'est supprimée.**
  - Un dossier **soumis** n'expire jamais : il attend les RH.
- **Tâches planifiées** (scheduler et cockpit Automatisations, via `ScheduledTaskRegistry`) :
  - `onboarding:expire` : chaque heure ; elle purge aussi les sessions échues.
  - `onboarding:scan-uploads` : toutes les 10 minutes.
  - `onboarding:retention` : chaque jour à 03:30, **en simulation**. L'option `--apply` n'est ajoutée que si `ONBOARDING_RETENTION_AUTO_APPLY=true`, une décision explicite à prendre après validation juridique par marché. Elle n'est jamais activée par ce lot, et la base partagée n'a pas été purgée.
- **Conservation** :
  - La durée est réglée par dossier (déclarée par les RH).
  - Le délai court depuis la validation, la révocation ou l'échéance réelle du lien.
  - La purge supprime les valeurs en attente, les sessions et les fichiers en quarantaine non ingérés, sans toucher aux documents du DMS.

## 6. Révision des exigences

- **Interface RH** (dialogue du dossier → « Modifier les éléments demandés ») :
  1. Consulter la liste actuelle et les éléments proposés pour le poste.
  2. Cocher ou décocher.
  3. Rendre obligatoire, seulement si une source le justifie.
  4. **Prévisualiser** (`POST …/items/preview`, sans écriture) : ajouts, retraits, obligations modifiées, réponses déjà reçues sur des éléments retirés, élément sensible ajouté, conséquence pour la recrue.
  5. Confirmer.
- **Après soumission** : la révision suit le circuit de demande de complément. Un message est obligatoire et le dossier passe à `changes_requested` avec ce message.
- **Ce qui est préservé** :
  - La photographie initiale et toutes les versions (`snapshot_history`).
  - Les documents déjà déposés et les valeurs reçues (jamais effacées).
  - Les décisions RH.
  - La confidentialité : un élément sensible ajouté exige une vérification.
- **Réponses à un élément retiré** : à la validation, elles passent à `not_requested`. Elles ne sont **jamais** écrites dans la fiche et sont purgées avec le dossier.
- **Obligation injustifiée** : refusée côté serveur (`required_unjustified`) si aucune règle (historique, configurée) ni proposition de module ne la porte. L'interrupteur « obligatoire » n'est proposé que lorsque c'est justifié. La photographie d'un dossier reste propre au dossier : aucune exigence opérationnelle n'est modifiée (vérifié par comparaison avant/après).

## 7. Statuts des fiches préparatoires

- **Marqueur** : `workforce_employees.preparatory_at`, posé à la création d'une fiche par le dossier d'intégration. La fiche est préparatoire tant qu'elle est `inactive` ; dès que les RH l'activent, elle devient une fiche ordinaire, sans autre écriture.
- **Reprise des fiches existantes** : la migration n'a marqué que les fiches créées par le flux ADR-796 (même instant que leur dossier, sans compte, inactives). Sur DEV, ce sont exactement les 6 fiches « E2E Recrue ».

| Surface | Avant | Après |
|---|---|---|
| Équipe (liste, filtre) | « Inactif » | « Recrue en préparation » (filtre dédié) ; un inactif historique reste « Inactif » |
| Conformité documentaire, campagnes (`PersonPopulationResolver`) | incluses | exclues (`Employee::operational()`) |
| Impact des exigences (`RequirementConfigService`) | comptées | exclues |
| Paie (`ComputePayrollUseCase`), planning (`PlanningBoardReadModel`), modèles de semaine | actifs seulement (déjà) | inchangé |
| Compteurs d'accueil Workforce (`active_employees`) | actifs seulement | inchangé |
| Documents de la personne | visibles dans sa fiche | inchangé (pièces déposées par la recrue) |

**Procédure de nettoyage proposée, à exécuter seulement après validation** :

```
php artisan onboarding:cleanup-fixtures 1771 1772 1773 1774 1775 1776          # simulation : inventaire
php artisan onboarding:cleanup-fixtures 1771 1772 1773 1774 1775 1776 --apply  # suppression
```

La commande n'accepte que des identifiants explicites, jamais un préfixe ni un motif. Elle fait une simulation par défaut et suit la règle du tout ou rien : elle refuse toute fiche qui n'est pas une fixture, c'est-à-dire :
- dont le nom ne commence pas par « E2E » ;
- qui n'est pas inactive ou qui a un compte ;
- qui a une trace opérationnelle : contrat, créneau, temps, absence, paie, ou toute table portant son `employee_id`.

Pour chaque fiche, elle supprime le dossier, les valeurs en attente, la quarantaine, les documents et leurs fichiers, les demandes et les valeurs RH, puis la fiche. L'historique d'audit est conservé, avec une entrée `onboarding.fixture_removed` par fiche.

**Recettes suivantes** : la recette ADR-796.1 crée sa propre fixture « E2E Recrue <horodatage> », puis la supprime en fin de parcours par son **id exact** via cette commande. Deux fiches de mise au point (1777, 1778) ont été retirées de cette façon pendant ce lot.

## 9. Confidentialité

| Point | Constat |
|---|---|
| Jeton dans les journaux | Aucun. Le jeton circule dans le corps de requête (jamais dans l'URL côté serveur) ; aucun middleware ne journalise les corps ; pas de Telescope ni de Sentry ; `grep '#t='` sur les journaux DEV : 0. Les erreurs d'envoi sont nettoyées des URL. |
| Code OTP dans l'audit | Aucun (test : code, jeton et adresses absents de `company_audit_logs`). |
| Jeton et code dans la file de tâches | Aucun : envoi immédiat. Les tâches d'analyse ne transportent que des identifiants. |
| Autre candidat / autre société | Aucun accès : session limitée à un dossier ; relance d'analyse, envoi et prévisualisation en 404 pour une autre société ou un autre dossier. |
| Documents sans autorisation | Aucun téléchargement public. Avant l'analyse, il n'existe aucun document DMS ; ensuite, la politique d'accès DMS s'applique. |
| Champs sensibles hors invitation | Seuls les éléments de la photographie sont accessibles, les sensibles seulement après vérification. |
| RH sans droit sensible | Valeurs masquées (`••••`), inchangé. |
| Autre employeur | Aucune divulgation : la communication est tracée par société (ADR-795.1). |
| Écrivain canonique | La validation passe toujours par `PersonFieldWriter` (contexte onboarding). |
| Contrats signés | Inchangés ; confirmation explicite exigée si un contrat est établi. |

**Fichiers et sauvegardes** : la quarantaine et le coffre DMS sont sur le disque privé. Les fichiers retirés de la quarantaine sont supprimés du disque, mais **peuvent subsister dans les sauvegardes** selon leur propre durée de conservation (hors de la portée de Leezr). La politique de sauvegarde doit donc être alignée sur les durées déclarées avant un usage réel. Mailpit (DEV) conserve localement les e-mails de test, liens et codes compris : c'est un outil local, à vider au besoin. Aucune base juridique nouvelle n'est introduite ; elles restent déclarées par l'entreprise.

## 11. Dépendances externes restantes

- **Moteur antivirus réel** : installer et superviser ClamAV, `DOCUMENT_SCANNER=clamav` et `CLAMAV_SOCKET`, mettre à jour les signatures. Sans lui, en production, les pièces du portail restent inutilisables (comportement voulu).
- **Envoi transactionnel en production** : SMTP authentifié, SPF/DKIM/DMARC, suivi des rebonds. L'échec de délivrance est tracé, mais les rebonds asynchrones ne remontent pas encore.
- **Worker de file en production** pour l'analyse. La tâche de reprise couvre son absence avec jusqu'à 10 min de latence.
- **Politique de sauvegarde** alignée sur les durées de conservation.
- **Validation juridique par marché** des finalités, bases et durées déclarées.
- **Étendre la quarantaine aux dépôts RH et self-service** : décision à prendre, hors périmètre.
- **Revue de sécurité externe** du portail public.
