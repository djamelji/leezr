## 1. Défaut de session : cause exacte

| Élément | Constat (code et base MySQL DEV) |
|---|---|
| Guards | `web` (provider `users`) et `platform` (provider `platform_users`), tous deux de type `session` |
| Driver | `SESSION_DRIVER=database`, table `sessions`, **un seul cookie** `leezr-session` partagé par les deux scopes ; Sanctum `statefulApi()`, garde Sanctum `['web']` |
| Clés de connexion | séparées dans le payload : `login_web_<sha1>` et `login_platform_<sha1>`. Pas de collision d'identité |
| Colonne `sessions.user_id` | clé étrangère vers `users.id` (`2026_03_18_000001_fix_sessions_user_fk`, ON DELETE CASCADE) |
| **Cause** | `Illuminate\Session\DatabaseSessionHandler::addUserInformation()` écrit `user_id = Auth::guard()->id()`, c'est-à-dire l'id du guard **par défaut au moment de l'écriture**. Or `auth:platform` appelle `shouldUse('platform')` : l'id d'un **PlatformUser** était donc écrit dans une colonne liée à **users** |
| Effet n° 1 | id absent de `users` → SQL 1452 → 500 sur `/api/platform/me` → **connexion Platform impossible**. En DEV : `finance-reader` (15), `ai-only` (16), `roles-only` (17), `gov-mgr` (18), `support-only` (19) |
| Effet n° 2 | id présent dans `users` → la session Platform était **rattachée silencieusement à un utilisateur Company sans rapport**. Supprimer cet utilisateur Company supprimait la session Platform (cascade). `dev@leezr.com` (id 2) ne fonctionnait que par coïncidence d'identifiant |
| Effet n° 3 (déconnexion) | chaque logout appelait `session()->invalidate()` : se déconnecter de la Platform **déconnectait aussi la Company** ouverte dans le même navigateur, et inversement |
| Usage applicatif de `user_id` | aucun. `SessionGovernance` ne lit que `last_activity` |

## 2. Correction retenue

1. **`App\Core\Auth\ScopedDatabaseSessionHandler`**, enregistré comme driver `database` via `Session::extend` dans `AppServiceProvider`. La configuration est inchangée.
   - Chaque identité va **dans sa propre colonne** : `user_id` ← guard `web`, `platform_user_id` ← guard `platform`.
   - Les identifiants sont lus directement dans le Store courant via la clé de connexion du guard : aucune requête, aucun effet « se souvenir de moi ». Une colonne vaut NULL quand le scope n'est pas connecté.
   - Si la migration n'est pas encore jouée, le handler l'ignore pour `platform_user_id`.
2. **Migration additive** `2026_12_02_000001_sessions_platform_user_id`.
   - Ajoute `platform_user_id` (nullable, indexée), avec une **clé étrangère vers `platform_users` ON DELETE CASCADE**.
   - Aucune ligne n'est modifiée ou supprimée. Jouée en DEV : les 22 sessions existantes sont conservées.
3. **`App\Core\Auth\ScopedLogout`**, utilisé par les deux contrôleurs de déconnexion.
   - Le guard du scope est déconnecté et sa clé 2FA en attente oubliée.
   - **Si l'autre scope est encore connecté**, l'id de session est renouvelé (`migrate(true)`, l'ancien id est détruit) et le jeton CSRF régénéré.
   - Sinon, invalidation complète, comme avant.

### Alternatives écartées

| Alternative | Raison |
|---|---|
| Créer un `User` miroir pour chaque `PlatformUser` | Interdit, et crée de fausses identités Company |
| Fusionner les tables d'identité | Interdit, et casserait le RBAC séparé |
| Supprimer la clé étrangère `sessions.user_id` | Désactive une contrainte d'intégrité ; la session Company y perdrait la suppression en cascade |
| Un cookie de session distinct par scope | Isolation la plus forte, mais elle touche Sanctum stateful, le CSRF, `SessionGovernance` et le boot frontend. Non nécessaire : les clés de connexion sont déjà séparées et testées. Gardée en piste (§8) |

## 3. Compatibilité Company / Platform

| Situation | Avant | Après |
|---|---|---|
| Session Company seule | `user_id` = utilisateur | **Inchangé**. `platform_user_id` NULL |
| Session Platform seule, id absent de `users` | **500**, connexion impossible | OK. `platform_user_id` = id, `user_id` NULL |
| Session Platform seule, id présent dans `users` | rattachée à un utilisateur Company sans rapport | `user_id` NULL : aucun lien |
| Les deux scopes dans le même navigateur | ligne écrite selon le dernier guard par défaut | `user_id` = Company, `platform_user_id` = Platform |
| Déconnexion Platform avec Company connectée | Company aussi déconnectée | Company conservée, id de session renouvelé |
| Déconnexion Company avec Platform connectée | Platform aussi déconnectée | Platform conservée, id renouvelé |
| Expiration pour inactivité (`SessionGovernance`) | invalide toute la session | **inchangé** : l'inactivité est mesurée sur la session commune |
| Autres drivers (file, redis, array, cookie) | ne stockent aucune identité | **inchangés** : seul `database` est étendu |
| Suppression d'un PlatformUser | — | ses sessions sont supprimées par la clé étrangère, celles de la Company restent |

Aucun utilisateur ne peut reprendre la session d'un autre scope :
- Sanctum ne lit que le guard `web` ;
- `auth:platform` ne lit que `login_platform_*`.

C'est vérifié par des tests, y compris avec deux identités de même numéro.

### État MySQL DEV après correctif

- 29 sessions, dont 8 Platform et 6 Company correctement rattachées.
- **13 anciennes lignes** écrites avant le correctif (dernière activité à 05:39 UTC) portent encore un id Platform dans `user_id`.
- Elles ne sont **pas supprimées** (règle du lot) : elles se réécrivent à leur prochaine requête, sinon elles expirent (120 min) et sont nettoyées par le ramasse-miettes standard.

Corrections associées :
- **Recherche globale** : chaque suggestion n'apparaît que si l'utilisateur détient la permission de sa page (même clé que la méta de la page). Une page dont le module est inactif reste refusée par le guard, qui renvoie vers le répartiteur.
- **Manifests** : les 5 anciens noms ont été retirés des `routeNames` de leurs modules (`jobdomains`, `documents`, `modules`, `notifications`, `fields`). Ce champ n'indique que l'existence d'écrans (`ModuleCommercialPolicy`) ; chaque module garde au moins une route réelle.
- **Menu « Accès »** : il exigeait `manage_platform_users` alors que la page accepte aussi `manage_roles` et `view_audit_logs` (ADR-801). Il passe en `anyPermission` sur les mêmes clés. Sinon, `roles-only` n'avait aucune entrée de menu et arrivait sur son compte.

## 5. Support : assigner sans administrer

### Ce qui est ajouté

- `GET api/platform/support/assignment-queue` : la file d'assignation. Projection minimale : `id`, `subject`, `status`, `priority`, `category`, `created_at`, `last_message_at`, `company {id, name}`, `assignee {id, prénom, nom}`.
  - Tickets ni résolus ni fermés par défaut ; recherche possible ; 50 par page au maximum.
  - **Exclus** : messages, notes internes, identité et e-mail du demandeur, SLA (`sla_status` masqué).
- `GET api/platform/support/assignees` : les agents **habilités à prendre en charge**, soit les détenteurs de `manage_support` par un rôle, plus le rôle `super_admin` (même règle que `PlatformUser::hasPermission`). Seuls l'id, le prénom et le nom sont renvoyés.
- `PUT …/assign` : refuse avec **422 `assignee_not_eligible`** un assigné non habilité.
- Interface : Communications → Support affiche la **file d'assignation** (`_SupportAssignmentQueue.vue`, `VDataTableServer` et `AppSelect` du stock) à qui a `assign_support` sans `manage_support`. Le bureau complet reste réservé à `manage_support`. Le menu Communications et la page acceptent désormais `assign_support`.

### Matrice d'accès

| Action | `manage_support` | `assign_support` seul | ni l'un ni l'autre |
|---|---|---|---|
| File d'assignation (projection minimale) | ✔ | ✔ | 403 |
| Liste des agents habilités | ✔ | ✔ | 403 |
| Assigner à un agent habilité | ✔ | ✔ | 403 |
| Assigner à un non-habilité (y compris à soi-même pour un assignateur seul) | **422** | **422** | 403 |
| Liste complète, détail, métriques, SLA | ✔ | **403** | 403 |
| Messages, notes internes | ✔ | **403** | 403 |
| Résoudre, fermer, priorité | ✔ | **403** | 403 |
| Documentation et paramètres | selon `manage_documentation` | **403** | 403 |
| Fiche ticket `support/:id` | ✔ | renvoyé vers sa file | renvoyé |

### Ce qui est préservé

- **Aucun rôle ni pivot existant n'a été modifié** : `admin` a les deux droits, `support_only` a `manage_support`.
- Les assignations historiques sont intactes : seules les **nouvelles** assignations sont contrôlées.

### Changement de comportement documenté

Assigner un ticket à un utilisateur Platform **sans** `manage_support` est désormais refusé.

Le test existant `SupportTicketTest::test_platform_admin_can_assign_ticket_to_another_admin` assignait à un « autre admin » **sans aucun rôle**. Il a été adapté : l'agent cible reçoit le rôle `admin`. C'est le changement voulu, pas une régression masquée.

## 8. Risques résiduels

| # | Risque | Proposition |
|---|---|---|
| R1 | Un seul cookie pour deux scopes : l'expiration d'inactivité et le CSRF sont communs | Cookie de session par scope, si l'on veut une isolation totale (lot dédié) |
| R2 | **PROD** : le même défaut existe probablement (même handler, même clé étrangère). La migration et le handler y sont nécessaires ; **non vérifié et non déployé** (périmètre DEV) | À inclure dans le prochain déploiement, après vérification de `SESSION_DRIVER` en PROD |
| R3 | 13 sessions DEV antérieures au correctif portent un id Platform dans `user_id` | Autocorrection à la prochaine requête, sinon expiration |
| R4 | L'assignateur seul ne voit pas le contenu du ticket : il répartit sur le sujet, la société et la priorité | Volontaire (minimum nécessaire). À revoir si le métier l'exige |
| R5 | Données de recette ajoutées : PlatformUser 21 et rôle `e2e_assign_8011` | À retirer sur décision, par identifiants exacts |
| R6 | Le toast Platform d'une notification sans lien ne mène nulle part : il rejoint la cloche | Conforme, puisqu'aucune page de liste Platform n'existe |
