## 1. Politique RBAC unifiée

### Chemins d'écriture inventoriés (pilotés par un utilisateur Company)

| Chemin | Avant | Après |
|---|---|---|
| `POST/PUT /company/roles` (éditeur Équipe → Rôles, avancé) | seulement « pas de permission d'administration sur un rôle opérationnel » : **un administratif pouvait s'ajouter n'importe quel droit, y compris sur son propre rôle** | politique de délégation complète, appliquée sur le **diff effectif**, y compris les droits retirés lors d'un passage en rôle opérationnel ; vérification **avant** toute écriture (rien n'est créé si c'est refusé) |
| `PUT /theme/role-visibility` (écrit `theme.view`) | aucune politique | même politique, avec toutes les vérifications faites avant la première écriture |
| `PUT /company/members/{id}` (affectation de rôle), invitation, accès depuis une fiche salarié | `assertCanAssignRole` : tenant, pas de modification de soi, administratif seulement par un administratif, dernier admin | **en plus** : un non-propriétaire n'affecte un rôle que si **toutes ses permissions** sont détenues par lui |
| Assistant de module et Équipe → Rôles par capacité | contrôles propres à l'assistant (ADR-803) | **le même moteur** (`CapabilityAccessService`) et **la même politique** |
| Initialisation de société, réconciliation, commandes | — | chemins système hors acteur : **inchangés** |

### Règles, au même endroit (`MembershipSecurityPolicy::rolePermissionChangeViolation`)

| Code | Règle |
|---|---|
| `other_company` | rôle d'une autre société |
| `protected_role` | le rôle `owner` ne se modifie pas |
| `operational_role` | pas de permission d'administration sur un rôle opérationnel |
| `own_role` | un non-propriétaire ne modifie pas son propre rôle (ni auto-élévation, ni auto-rétrogradation), comme pour l'affectation (ADR-752) |
| `beyond_your_rights` | **délégation** : un acteur administratif n'ajoute ni ne retire que des permissions **qu'il détient** ; un non-administratif ne délègue rien |

- **`roles.manage`** est le pouvoir de donner des droits : **seul le propriétaire** l'ajoute à un rôle. Une permission possédée n'est donc pas automatiquement délégable.
- Les permissions sensibles sont contrôlées explicitement :
  - permissions d'administration réservées aux rôles de gestion ;
  - bundles `sensitive` présentés à part ;
  - délégation limitée à ce que l'acteur détient.
- Aucun contournement par API directe : les cinq points d'entrée appellent la même fonction, et les tests le vérifient sur chacun.

## 2. Sémantique des capacités et parcours UI

- **Le RBAC stocke des permissions effectives, jamais l'intention « accordée par le bundle X ».** Une capacité est entière (`full`) ou partielle (`partial`), c'est tout.
- **Seuls les changements explicites** sont appliqués. Les permissions hors des capacités modifiées ne sont jamais touchées : les personnalisations historiques sont **conservées** (testé).
- **Capacité partielle** : signalée, jamais complétée ni réduite sans clic (testé).
- **Recouvrement** : retirer une capacité conserve les permissions qu'une autre capacité, entièrement détenue, exige encore (testé avec `team` et `time_validation`).
- **Capacité contenue dans celle qu'on retire** : elle est considérée comme impliquée, donc retirée avec elle. L'aperçu la liste en **« capacités qui ne seraient plus entièrement attribuées »**, et l'application exige `confirm_affected`. Sans cette confirmation, la réponse est `422 affected_capabilities`.
- **Effet de bord positif** : les capacités qui deviennent complètes sont signalées.
- **Aperçu exact**, partagé par l'assistant et par Équipe → Rôles (`CapabilityChangePreview.vue`) : « +N / −M droits » par rôle, la raison d'un blocage, les capacités affectées, une case de confirmation, et les identifiants techniques en mode avancé.
- **Équipe → Rôles** : bascule **« Par capacité »** (par défaut) ou **« Par rôle (avancé) »** :
  - « Par capacité » réutilise `ModuleCapabilityAccess` et l'aperçu, sur l'API `/company/role-capabilities/{module}` (`roles.view` pour lire, `roles.manage` pour écrire) ; `?module=` ouvre directement un module ;
  - « Par rôle » garde la matrice existante, permission par permission, désormais soumise à la même politique.

## 3. Fiabilité de l'état « Prêt »

- **Vérification à la lecture**, sans aucune synchronisation.
- **Migration additive** : `company_module_setups.access_fingerprint`, enregistré à la confirmation.

| Événement après « Prêt » | Effet (testé) |
|---|---|
| Permissions d'un rôle modifiées hors assistant (éditeur, Équipe par capacité, thème) | `needs_review` (« À revoir »), raison `access_changed` |
| Rôle supprimé | `needs_review` (`access_changed`) |

| Désactivation | `suspended` |
| Réactivation | **`in_progress`**, avec choix et droits conservés, et une nouvelle confirmation exigée |

- « Reconfirmer » revérifie tout, puis rétablit « Prêt » avec une empreinte neuve.
- Le statut « À revoir » apparaît dans l'assistant (bandeau listant les raisons) et dans la liste des modules (puce).
- Les modules `legacy` (activés avant ADR-803) sont inchangés.
- Le contrat des prérequis gagne `staleReasons()`, implémenté par Workforce.

## 4. Recette complète isolée, réellement exécutée

**Fixture fictive**, créée par script et sans aucune activation, avec ses identifiants exacts consignés :
- un JobDomain inactif `e2e_8031` ;
- un preset RBAC **fictif publié et associé** à ce JobDomain (Chef → `workforce.manager`, Agent → `workforce.timesheet_employee`) ;
- une société `e2e-8031-*` (offre pro, marché FR) ;
- trois comptes `@leezr.invalid` ;
- deux rôles **sans aucun droit** ;
- un salarié **sans compte**.

Workforce coûte 0 € à l'activation pour cette offre : aucune donnée de facturation n'est créée. Le preset logistique **n'a pas** été publié.

## 7. Résidus

| # | Point | Proposition |
|---|---|---|
| R1 | **Changement de comportement voulu** : un administratif non propriétaire ne peut plus modifier son propre rôle, ajouter `roles.manage`, déléguer un droit qu'il ne détient pas, ni affecter un rôle plus puissant que lui. Le propriétaire n'est pas concerné | À communiquer aux administrateurs |
| R2 | Les droits historiques **déjà** attribués hors politique (avant ce lot) ne sont pas revus automatiquement | Rapport de conformité RBAC (lecture seule), sur GO |
| R3 | `settings_changed` repose sur l'horodatage des politiques Workforce : une écriture technique sans changement de valeur suffit à demander une revue (faux positif prudent) | Assumé (prudence) |
| R4 | Les deux E2E historiques corrigés sont exécutés en lecture seule sur la société 1, et non sur une fixture | Fixture enrichie (fiche, paie) dans un lot de maintenance E2E |
| R5 | Les autres modules n'ont pas encore d'assistant | Généralisation sur GO (liste ADR-803 §12) |
