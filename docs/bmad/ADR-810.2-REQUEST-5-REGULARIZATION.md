## 3. Chemin métier

Le moteur n'a pas de transition `submitted → requested`. La remise à « demandée » n'existait que dans la suppression d'une pièce (ADR-810.1), sans événement. Les autres options étaient écartées :

- **Annuler puis rouvrir** aurait tracé une fausse annulation et réécrit `requested_at`.
- **Une écriture SQL directe** est interdite.

Ajout au moteur existant (`DocumentRequestService`), sans nouveau moteur :

- `regularizeMissingFile(request, actor, reason, context)`.
  - **Refusée** si la demande n'est pas dans un état « fichier fourni » (`FILE_BACKED_STATES`).
  - **Refusée** si une pièce existe (`evidenceDocument() !== null`). Dans ce cas l'état est légitime.
  - Dans une transaction : `status = requested`, `submitted_at = null`, plus un événement `regularized` (nouvelle constante `DocumentRequestEvent::E_REGULARIZED`) dont les métadonnées contiennent `previous_status`, `new_status` et `file_present = false`.
- Le reste de la demande est inchangé : `requested_at`, `created_at`, sujet et type.
- Elle n'est exposée par **aucune route** et n'est utilisée que pour cette régularisation.

Exécution : depuis `tinker`, appel de ce service sur la demande 5, après réassertion des contrôles (`user_id = 2`, type 2, `submitted`, aucune preuve).

## 6. Tests

- `Adr8101DocumentRequestIntegrityTest::test_regularizing_a_submitted_request_without_a_file`. Il reproduit la forme exacte de la demande 5 (insertion SQL, événement `submitted` sans acteur) et vérifie :
  - l'approbation sans fichier est refusée (422), avant comme après ;
  - la régularisation est refusée sur une demande « demandée » ;
  - la régularisation donne `requested` et `submitted_at = null` ;
  - l'événement historique est conservé et l'événement `regularized` contient ses métadonnées ;
  - les autres demandes sont inchangées et aucune pièce n'est créée ;
  - les trois vues affichent « Demandé » ;
  - la personne peut ensuite déposer (`submitted`) ;
  - une demande adossée à une pièce ne peut plus être « régularisée ».
